# 設計判断（ADR）

## ADR-001: リポジトリを責務別に分ける

- **決定**: Frontend、Backend、Platform/Infraの3リポジトリを使う。
- **理由**: UI/API/クラウド基盤を個別にビルド・レビューでき、API契約と環境定義の責任者が明確になる。
- **帰結**: OpenAPI等のAPI契約をBackendで管理し、Frontendのクライアントとこのリポジトリの説明を同期する。横断変更は複数PRの互換性を確認する。

## ADR-002: Markdownをレポート正本にする

- **決定**: レポートの正本形式はMarkdown。HTMLは安全にレンダリングして画面で表示する形式とする。
- **理由**: Markdownは差分確認、再生成、テキスト検索、将来の別表示形式への変換が容易。HTMLだけを正本にすると生成物の検証・安全な再表示が難しい。
- **帰結**: 生HTMLの実行を禁止し、HTML変換時にサニタイズする。出典メタデータは形式化してMarkdown本文とは別に保存する。

## ADR-003: Blobを正本、Searchを派生インデックスにする

- **決定**: Blob Storageにレポート原本を保存し、Azure AI Searchには検索用フィールドとチャンクを格納する。
- **理由**: インデックスは作り直し可能な派生データにでき、保存物の保持と検索スキーマ変更を独立させられる。
- **帰結**: Blob書き込み後にSearchへ反映する。削除・再インデックス・重複登録を扱うジョブと状態管理が必要。

## ADR-004: UIからFoundryを直接呼び出さない

- **決定**: FrontendはBackend APIのみ呼び出し、FoundryやStorage/Searchの資格情報を持たない。
- **理由**: 認可、レート制限、監査、プロンプト・ツールの境界、保存処理を一元化する。
- **帰結**: BackendからAzureリソースへはManaged Identityを優先し、長期共有キーを避ける。

## ADR-005: 環境依存のAIリソースは段階導入する

- **決定**: 初期BicepはFoundry project/モデル/agent、MCPサーバー、SRE Agentを自動作成しない。
- **理由**: リージョン、モデル利用可否・クォータ、サービス仕様と権限が環境依存。誤った仮定でデプロイ可能と表示しないため。
- **帰結**: 各統合の設定、権限、ネットワーク、実際のエンドツーエンド検証を追加し、条件が固まった時点でテンプレート化する。

## ADR-006: 開発用プロバイダーと本番プロバイダーを分ける

- **決定**: ローカル開発では明示的なローカル／サンプルプロバイダーを許可し、本番モードでは実プロバイダー未設定を起動エラーにする。
- **理由**: デモ用の固定回答を本物の調査結果やFoundry接続として誤認させないため。
- **帰結**: UIにもローカルモードの表示を付け、サンプル出典は公式ソースの実取得結果として表示しない。
