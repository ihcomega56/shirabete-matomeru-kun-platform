# 運用・監視

## 監視の基本

Azure SRE Agentの有無にかかわらず、通常の監視、アラート通知、オンコール手順が成立することを前提にします。SRE Agentは調査支援の追加レイヤーとし、可用性監視そのものの代替にはしません。

| 観点 | 推奨シグナル |
| --- | --- |
| 可用性 | APIのヘルスエンドポイント、Frontendの合成監視、リージョン別失敗 |
| レイテンシ | API P50/P95/P99、agent実行、Blob/Search依存先の時間 |
| エラー | HTTP 5xx/4xx比率、Foundry/MCP/Blob/Searchのエラー、タイムアウト |
| 品質 | 出典付き回答率、レポート保存率、Search反映遅延、再試行数 |
| コスト | モデル使用量、Search SKU/容量、App Service稼働、Storage増加 |
| セキュリティ | Entra認証失敗、RBAC拒否、異常な質問レート、管理操作ログ |

回答本文や認証トークン、シークレット、機微なユーザー質問をアプリケーションログに記録しないでください。相関ID、実行ID、ツール名、エラー分類、経過時間など運用に必要な最小限を記録します。

## 初期アラート候補

- APIの5xx率または失敗数が一定時間しきい値を超える。
- 合成可用性チェックが複数回連続で失敗する。
- API P95レイテンシがSLO目標を超える。
- レポートのBlob保存失敗、Search反映遅延、インデックスエラーが増える。
- Foundry/MCP利用エラーまたは時間切れが急増する。
- モデル消費量・月次推定額が予算しきい値を超える。

しきい値は実トラフィックとSLOを測定して決める。初期値のまま本番アラートとして扱わない。

## インシデント時の初動

1. Azure Service Healthと依存先の稼働状態を確認する。
2. 相関IDでApplication Insightsのトレースを確認し、API、Foundry/MCP、Blob、Searchを切り分ける。
3. レポートのBlob保存有無を確認し、Search反映失敗なら重複作成を避けて再インデックスする。
4. ユーザー影響、データ影響、リージョン、開始時刻を記録し、必要ならagent呼び出しを無効化して明示的な縮退応答に切り替える。
5. 復旧後に検索再構築・データ整合性を確認し、原因と再発防止を記録する。

## Azure SRE Agentとの連携

- 接続先リソース、ワークスペース、アラート、ログ範囲を最小限にする。
- まず読み取り調査と推奨アクションから開始する。デプロイ、再起動、権限変更などの変更操作は人間の承認なしに実行しない。
- SRE Agentの提供リージョン、GA/プレビュー状態、権限モデル、監査と課金を利用環境で確認してから有効化する。
- 実行内容と承認者を監査し、調査で参照するログに機微情報を含めない。

## バックアップと復旧

- Blobの冗長性、soft delete/versioning、ライフサイクル、復旧目標（RPO/RTO）を環境ごとに設定する。
- Azure AI Searchインデックスは再作成可能な派生データとして扱い、Blobからの再構築手順を用意する。
- Bicepで構成を再現可能にし、アプリケーションとインフラの変更履歴をPRでレビューする。
- 復旧訓練では、保存済みMarkdownと出典メタデータが復元され、同じレポートを検索できることを確認する。
